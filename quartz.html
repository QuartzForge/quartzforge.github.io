O roteador é resolvido antes do programa existir.

Rotas, parâmetros e middlewares viram estrutura de dados em tempo de compilação. No boot não há varredura de arquivos nem registro dinâmico: a tabela já está lá, e os tipos dos parâmetros também.

src/app.cr 
class Billing < Quartz::App
  use Quartz::RequestID
  use Quartz::Logger, format: :json
  use RateLimit, per: 100, every: 1.minute

  scope "/v1" do
    get "/health" { |c| c.json(status: "ok") }

    resources "/invoices", InvoicesController,
              only: %i[index show create], as: :invoices

    ws "/events", EventsSocket
  end
end

# reverse URL from the route name
Billing.path(:invoices_show, id: invoice.id)
# => "/v1/invoices/018f...."
class InvoicesController < Quartz::Controller
  # the query string becomes a type — no Hash(String, String)
  struct IndexQuery
    include Facet::Schema
    field page   : Int32 = 1, gte: 1
    field status : String?, in: %w[draft sent paid]
  end

  def index(c, q : IndexQuery)
    c.json Invoice.query
      .where(status: q.status)
      .preload(:customer)
      .page(q.page)
  end

  def show(c, id : UUID)
    invoice = Invoice.find(id, preload: :customer)
    return c.problem(404, "invoice not found") unless invoice
    c.json(invoice)
  end
end
class RateLimit
  include Quartz::Middleware

  def initialize(@per : Int32, @every : Time::Span)
  end

  # call receives the next link — the chain is explicit
  def call(c : Quartz::Context, next_link)
    key = c.header("X-Api-Key") || c.remote_ip

    if Bucket.exceeded?(key, @per, @every)
      c.header("Retry-After", @every.total_seconds.to_i)
      return c.problem(429, "rate limit exceeded")
    end

    next_link.call(c)
  end
end

O que vem na caixa

Suficiente para uma API de produção, e nada além.

Roteador em radix tree

Construído na compilação a partir das declarações. Parâmetros de rota chegam já convertidos para o tipo declarado — UUID, Int64, enum.

Middlewares em cadeia explícita

Cada middleware recebe o próximo elo e decide se chama. Sem hooks globais, sem ordem implícita definida por outro arquivo.

Erros em RFC 9457

c.problem(status, …) devolve application/problem+json com o RequestID no campo instance.

Streaming, SSE e WebSocket

Na mesma aplicação e no mesmo roteador. Um handler de socket é uma classe com on_message.

Contexto por requisição

RequestID propagado para o log, para a resposta de erro e para os jobs enfileirados durante a requisição.

Testes sem subir servidor

Quartz::Test injeta requisições direto na cadeia de middlewares — sem porta, sem socket.

Superfície principal

Dez métodos cobrem quase tudo.

Métodos principais de quartz
AssinaturaO que faz
get / post / put / patch / deleteDeclara uma rota com bloco ou controller.
scope(prefix, via:)Agrupa rotas sob um prefixo e uma pilha de middlewares.
resources(path, controller, only:)Gera o conjunto REST a partir dos métodos do controller.
ws(path, handler)Registra um handler de WebSocket no mesmo roteador.
use(middleware, **opts)Adiciona um elo à cadeia, na ordem de declaração.
c.param(name, Type)Lê e converte um parâmetro; responde 400 se não converter.
c.json(value, status:)Serializa e responde com o content-type correto.
c.problem(status, detail)Resposta de erro no formato RFC 9457.
c.stream { |io| … }Resposta em chunks, com backpressure respeitado.
App.path(:name, **params)Gera a URL de uma rota nomeada.
Quando não usar quartz

Se você precisa de renderização de HTML com layouts, helpers de formulário e assets pipeline, quartz vai ficar no seu caminho — ele é feito para APIs. Um framework MVC completo é a escolha certa nesse caso.
