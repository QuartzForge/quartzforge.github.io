require "quartz"
require "./controllers/*"

class Billing < Quartz::App
  # middlewares run in declaration order
  use Quartz::RequestID
  use Quartz::Logger, format: :json
  use Quartz::CORS, origins: ["https://app.example.com"]

  scope "/v1" do
    get "/health" { |c| c.json(status: "ok", uptime: Quartz.uptime) }

    resources "/invoices", InvoicesController, only: %i[index show create]

    scope "/admin", via: Auth::RequireRole.new(:admin) do
      resources "/customers", CustomersController
    end
  end
end

Billing.run(host: "0.0.0.0", port: 3000)
require "facet"

struct NewInvoice
  include Facet::Schema

  field customer_id : UUID
  field due_at      : Time, gte: -> { Time.utc }
  field line_items  : Array(LineItem), size: 1..200
  field note        : String?, size: ..280

  validate :positive_total do |f|
    f.error(:line_items, :total_must_be_positive) if f.total_cents <= 0
  end

  def total_cents : Int64
    line_items.sum(&.amount_cents)
  end
end

# returns a typed object or the errors — never a loose Hash
case result = NewInvoice.validate(body)
when Facet::Valid   then InvoicesService.create(result.value)
when Facet::Invalid then c.problem(422, result.errors) # RFC 9457
end
require "obsidian"

class Invoice < Obsidian::Model
  table :invoices

  column id          : UUID = UUID.v7, primary: true
  column total_cents : Int64
  column status      : Status
  column issued_at   : Time

  belongs_to customer   : Customer
  has_many   line_items : LineItem

  enum Status
    Draft; Sent; Paid
  end
end

# the relation must appear in the preload…
invoices = Invoice.query
  .where(status: :paid)
  .preload(:customer, line_items: :product)
  .order(issued_at: :desc)
  .limit(50)

invoices.each { |i| puts "#{i.customer.name} — #{i.line_items.size} items" }

require "pulse"

struct SendInvoice
  include Pulse::Job

  queue "mailers"
  retries 5, backoff: :exponential
  unique_for 10.minutes

  def initialize(@invoice_id : UUID)
  end

  def perform
    invoice = Invoice.find!(@invoice_id, preload: :customer)
    Mailer.invoice(invoice).deliver
  end
end

SendInvoice.new(invoice.id).enqueue(in: 30.seconds)

# the worker is the same binary; the queue is your Postgres.
# SKIP LOCKED to claim, LISTEN/NOTIFY to wake up.
Pulse::Worker.new(queues: {"mailers" => 4, "default" => 8}).run
require "vault"

Vault.configure do |v|
  v.provider :google, id: ENV["GOOGLE_ID"], secret: ENV["GOOGLE_SECRET"],
                     scopes: %w[openid email profile]
  v.provider :github, id: ENV["GITHUB_ID"], secret: ENV["GITHUB_SECRET"],
                     scopes: %w[read:user user:email]
  v.redirect_uri "https://app.example.com/oauth/:provider/callback"
end

get "/oauth/:provider" do |c|
  c.redirect Vault.authorize_url(c.param("provider"), state: c.session.csrf)
end

get "/oauth/:provider/callback" do |c|
  case r = Vault.exchange(c.param("provider"), code: c.param("code"))
  when Vault::Success then Session.open(c, identity: r.identity)
  when Vault::Failure then c.problem(401, r.reason)
  end
end

Cinco projetos, zero garimpo

Cada peça resolve um escopo. Nenhuma obriga a próxima.

Você pode subir uma API só com quartz, usar facet dentro de um projeto Lucky, ou colocar pulse num serviço que já existe. O ganho de usar tudo junto é o compilador enxergar a aplicação inteira.

O argumento principal

O N+1 não chega em produção porque não passa do build.

Em quase toda ORM, esquecer um preload é um problema que só aparece sob carga. Em obsidian, a query devolve um tipo que só conhece as relações que você carregou — acessar qualquer outra é erro de compilação.

src/reports/overdue.cr 
invoices = Invoice.query
  .where(status: :overdue)
  .preload(:customer)           # only customer was loaded
  .limit(200)

invoices.each do |invoice|
  charge(invoice.customer.email)      # ✓ loaded
  record(invoice.payments.last)      # ✗ not loaded
end
$ forge build 
Compiling billing…

Error in src/reports/overdue.cr:7:18

  relation `payments` was not preloaded
  on Invoice::Loaded(:customer)

  hint: .preload(:customer, :payments)

1 error · no binary produced
  • A mensagem já traz a correçãoO compilador sabe qual preload falta porque ele montou o tipo.
  • Vale para o editor tambémO mesmo tipo alimenta o autocompletar: relações não carregadas não aparecem na lista.
  • Sem lazy loading escondidoNão existe fallback silencioso que dispara uma query dentro de um laço.

Como as peças se encaixam

Acoplamento por contrato, não por herança.

Os projetos se conhecem por interfaces pequenas. quartz aceita qualquer validador que responda a #validate; pulse usa a mesma conexão que obsidian já abriu. Trocar uma peça não derruba as outras.

quartz recebe a requisição, roteia, responde
body cru
facet valida e devolve tipo
vault identidade do usuário
valor tipado
obsidian lê e grava, relações verificadas
pulse enfileira o que é lento
mesma conexão
PostgreSQL dados e fila no mesmo lugar
  • Um binário para tudoAPI, worker, migrações e tarefas agendadas saem do mesmo build. O deploy é copiar um arquivo.
  • Uma dependência de infraPostgres. A fila mora nele, as sessões podem morar nele, e não há Redis obrigatório no caminho.
  • Sem descoberta em runtimeRotas, colunas e jobs são resolvidos na compilação. Não há varredura de diretórios no boot.
  • Macros só onde valem a penaMetaprogramação fica nas definições de schema e coluna. O resto é Crystal comum, que o LSP entende.

Princípios

Quatro decisões que explicam o resto.

Explícito > automágico

Nenhum arquivo é carregado por convenção de nome. Se algo roda, está escrito em algum lugar que você pode abrir.

O tipo é a documentação

Assinaturas carregam a intenção. Um Facet::Valid(NovaFatura) não precisa de comentário explicando o que já passou.

Cada peça vive sozinha

Nenhum projeto depende de outro do QuartzForge para funcionar. Adotar um não obriga a adotar cinco.

Erro é dado, não exceção

Validação, OAuth e persistência devolvem resultados que o case obriga você a tratar.

Prova, não promessa

Cargas nomeadas, comandos publicados, números só depois do CI.

Não publicamos comparativos até o harness rodar em máquina neutra e o resultado estar reproduzível por qualquer pessoa. Enquanto isso, o que existe é o comando — rode você mesmo.

API JSON simples, 1 rota, sem banco forge bench http --scenario hello --duration 30s
— aguardando CI
Listar 500 faturas com duas relações pré-carregadas forge bench db --scenario preload-2 --rows 500
— aguardando CI
Enfileirar e processar 10 mil jobs em Postgres forge bench queue --jobs 10000 --workers 8
— aguardando CI
Build limpo do projeto de exemplo, sem cache forge build --release --no-cache
— aguardando CI
Por que os campos estão vazios

Um número sem metodologia é marketing. As linhas acima ficam com traço até o repositório quartzforge/benchmarks publicar os resultados assinados pelo CI, com hardware e versão de compilador declarados.
