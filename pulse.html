pulse
Fila de jobs
beta · v0.8

O job e o dado entram na mesma transação.

A fila é uma tabela no seu Postgres. Se a transação que criou a fatura der rollback, o job que ia enviá-la desaparece junto — o caso clássico de “enfileirou algo que nunca existiu” deixa de ser possível. 

# shard.yml
dependencies:
  pulse:
    github: quartzforge/pulse
    version: ~> 0.8
Ver o guia Ver o ecossistema

Crystal ≥ 1.14·PostgreSQL 14+·sem Redis·MIT

src/jobs/send_invoice.cr 
struct SendInvoice
  include Pulse::Job

  queue "mailers"
  retries 5, backoff: :exponential, cap: 1.hour
  unique_for 10.minutes, by: :invoice_id
  timeout 30.seconds

  def initialize(@invoice_id : UUID)
  end

  def perform
    invoice = Invoice.find!(@invoice_id, preload: :customer)
    Mailer.invoice(invoice).deliver
  end

  # called after the retries are exhausted
  def on_dead(error : Exception)
    Alerts.notify("invoice #{@invoice_id} never went out", error)
  end
end
require "pulse"
require "./jobs/*"

# concurrency per queue, not one global number
worker = Pulse::Worker.new(queues: {
  "mailers" => 4,
  "reports" => 2,
  "default" => 8,
})

# graceful shutdown: finish whatever is in flight
Signal::TERM.trap { worker.drain(within: 25.seconds) }

worker.run

# no aggressive polling: the worker sits on LISTEN and
# only runs SELECT ... FOR UPDATE SKIP LOCKED when it is
# woken by NOTIFY (or every 5s, as a safety net).
# periodic tasks in the same binary, no crontab

Pulse.schedule do |s|
  s.daily("03:15", tz: "America/Sao_Paulo") do
    CloseAccountingPeriod.new.enqueue
  end

  s.every(15.minutes) do
    SyncPaymentSlips.new.enqueue
  end

  # the lock is Postgres': with N replicas, only one fires
  s.cron("0 8 * * 1") { WeeklyDigest.new.enqueue }
end

O mecanismo

Três recursos do Postgres, nenhum serviço a mais.

SKIP LOCKED

Cada worker pega o próximo job disponível sem esperar pelos que já estão travados. É o mesmo mecanismo que os bancos usam para filas há anos — só que aqui está declarado, não emulado.

LISTEN / NOTIFY

O worker dorme até um NOTIFY chegar. Sem polling de segundo em segundo martelando o banco à toa.

Locks consultivos

Garantem que a agenda dispare uma vez só, mesmo com várias réplicas do binário rodando ao mesmo tempo.

o SQL que o worker executa
UPDATE pulse_jobs SET
  state     = 'running',
  attempts  = attempts + 1,
  locked_at = now()
WHERE id IN (
  SELECT id FROM pulse_jobs
  WHERE queue = $1
    AND state = 'pending'
    AND scheduled_at <= now()
  ORDER BY priority DESC, scheduled_at
  LIMIT $2
  FOR UPDATE SKIP LOCKED
)
RETURNING id, class_name, payload;
  • Você pode auditar a fila com SQLÉ uma tabela. SELECT nela responde “o que está travado agora” sem painel nenhum.
  • Backup da fila é o backup do bancoNão existe estado crítico morando num Redis sem persistência.
  • Fila morta como tabelaJobs esgotados ficam com estado dead e o erro serializado — reprocessar é um UPDATE.
  • Métricas por filaProfundidade, latência de espera e taxa de falha expostas em /metrics no formato Prometheus.

Declarações do job

O comportamento fica no topo da classe.

Declarações disponíveis em um job do pulse
DeclaraçãoPadrãoEfeito
queue "name"defaultFila lógica; a concorrência é configurada por fila no worker.
retries n, backoff:3, exponencialQuantas vezes tentar e como espaçar. cap: limita o intervalo.
unique_for span, by:desligadoDescarta duplicatas na janela, usando os campos indicados como chave.
timeout span5 minJob que passar disso é interrompido e volta para retentativa.
priority n0Maior valor sai primeiro dentro da mesma fila.
enqueue(in:, at:)agoraAgendamento relativo ou absoluto.
on_dead(error)—Gancho chamado quando as retentativas se esgotam.
Quando não usar pulse

Em volumes muito altos e sustentados — dezenas de milhares de jobs por segundo — a fila passa a competir por I/O com as consultas da aplicação, e um broker dedicado faz mais sentido. Enquanto a fila couber confortavelmente no seu Postgres, ter uma peça a menos na infra costuma valer mais.
