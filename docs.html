Documentação/Começando

Início rápido

Em torno de dez minutos: instalar o CLI, criar o projeto, subir uma rota, validar o corpo da requisição, gravar no banco e mandar o trabalho lento para a fila.

Pré-requisitos

Crystal 1.14 ou superior e um PostgreSQL 14+ acessível. O CLI checa os dois antes de gerar o projeto.

Instalação

O forge é um binário único. Ele não é obrigatório — dá para usar os shards direto no shard.yml — mas ele cuida de scaffolding, migrações e build de produção. 

$ curl -fsSL https://get.quartzforge.org | sh
$ forge --version
$ brew tap quartzforge/tap
$ brew install forge
$ git clone https://github.com/quartzforge/forge
$ cd forge && shards build --release
$ cp bin/forge /usr/local/bin/

Criando o projeto:

$ forge new billing --db postgres
$ cd billing
$ forge dev        # rebuilds and restarts on every file save

Estrutura do projeto

Nada aqui é carregado por convenção de nome de pasta. Os require ficam em src/faturamento.cr e são a única fonte da verdade sobre o que entra no build.

Primeira rota

Rotas são declaradas dentro da classe da aplicação. O bloco recebe o contexto da requisição; controllers entram quando a rota deixa de caber em três linhas.

src/app.cr
require "quartz"

class Billing < Quartz::App
  use Quartz::RequestID
  use Quartz::Logger, format: :json

  scope "/v1" do
    get "/health" { |c| c.json(status: "ok") }

    # :id arrives typed; if it is not a UUID, quartz replies 400 on its own
    get "/invoices/:id" do |c|
      id = c.param("id", UUID)
      c.json(InvoicesService.find(id))
    end
  end
end

Billing.run(port: 3000)

Confira com o CLI, que também lista as rotas registradas na compilação:

$ forge routes
GET   /v1/health
GET   /v1/invoices/:id   (id: UUID)

Validando a entrada

Um schema do facet é um struct comum. Validar devolve Facet::Valid ou Facet::Invalid — o case obriga você a tratar os dois.

src/schemas/new_invoice.cr
require "facet"

struct NewInvoice
  include Facet::Schema

  field customer_id : UUID
  field due_at      : Time, gte: -> { Time.utc }
  field line_items  : Array(LineItem), size: 1..200
end
src/controllers/invoices_controller.cr
def create(c : Quartz::Context)
  case r = NewInvoice.validate(c.body)
  when Facet::Valid
    invoice = InvoicesService.create(r.value)
    c.json(invoice, status: 201)
  when Facet::Invalid
    c.problem(422, r.errors)
  end
end

O que o cliente recebe quando falha

422 · application/problem+json
{
  "type": "https://quartzforge.org/errors/validation",

}

Modelo e migração

O modelo declara colunas e relações; a migração é um arquivo versionado com timestamp. O obsidian compara os dois no build e avisa quando divergem.

src/models/invoice.cr 
class Invoice < Obsidian::Model
  table :invoices

  column id          : UUID = UUID.v7, primary: true
  column total_cents : Int64
  column status      : Status = Status::Draft
  column issued_at   : Time

  belongs_to customer   : Customer
  has_many   line_items : LineItem
end
class CreateInvoices < Obsidian::Migration
  def up
    create_table :invoices do |t|
      t.uuid    :id, primary: true
      t.uuid    :customer_id, references: :customers, on_delete: :restrict
      t.bigint  :total_cents, null: false
      t.enum    :status, %i[draft sent paid], default: :draft
      t.timestamptz :issued_at, null: false
    end

    create_index :invoices, %i[status issued_at]
  end

  def down
    drop_table :invoices
  end
end
$ forge db migrate
→ 20260819103000_create_invoices  applied
Sempre declare o preload

Acessar uma relação fora do preload é erro de compilação, não erro de runtime. É o comportamento pretendido — veja obsidian.

Job em background

O pulse grava o job na mesma transação que gravou o dado. Se a transação der rollback, o job some junto — não existe o caso de enfileirar algo que nunca foi persistido.

src/jobs/send_invoice.cr
struct SendInvoice
  include Pulse::Job

  queue "mailers"
  retries 5, backoff: :exponential

  def initialize(@invoice_id : UUID)
  end

  def perform
    invoice = Invoice.find!(@invoice_id, preload: :customer)
    Mailer.invoice(invoice).deliver
  end
end

# inside the service, in the same transaction:
Obsidian.transaction do
  invoice = Invoice.create!(attrs)
  SendInvoice.new(invoice.id).enqueue
end
$ forge worker --queues mailers:4,default:8

Login com OAuth

O vault normaliza o retorno de cada provedor numa única estrutura Vault::Identity, com id, email, name e avatar_url.

src/oauth.cr
Vault.configure do |v|
  v.provider :google, id: ENV["GOOGLE_ID"], secret: ENV["GOOGLE_SECRET"]
  v.redirect_uri "https://app.example.com/oauth/:provider/callback"
end

get "/oauth/:provider/callback" do |c|
  case r = Vault.exchange(c.param("provider"), code: c.param("code"))
  when Vault::Success then Session.open(c, identity: r.identity)
  when Vault::Failure then c.problem(401, r.reason)
  end
end

Implantação

O build de release gera um binário estático. API, worker e migrações são o mesmo arquivo com subcomandos diferentes — não há duas imagens para manter em sincronia. 

$ forge build --release --static
→ bin/billing

$ ./billing db migrate
$ ./billing serve --port 3000
$ ./billing worker --queues mailers:4

Formato de erro

Toda resposta de erro segue a RFC 9457 (application/problem+json). O campo errors é uma extensão do QuartzForge e só aparece em falhas de validação.

Campos da resposta de erro
CampoSempre presenteDescrição
typesimURI que identifica a classe do problema.
titlesimResumo legível, estável entre ocorrências.
statussimMesmo código do cabeçalho HTTP.
instancesimTraz o RequestID, para casar com o log.
errorsnãoLista de field, rule e detail.
